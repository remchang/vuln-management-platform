## 一、需求分析

### 1.1 要解决的问题

安全工具能一次吐出几十条告警，但**告警不是结论**。真实工作流缺的是：

| 编号 | 缺什么 | 后果 |
| --- | --- | --- |
| P1 | 没有授权边界 | 可能违法测试 |
| P2 | 没有去重 | 每次导入都在重复创建，告警越滚越多 |
| P3 | 没有复核结论 | 误报和真阳性混在一起，没人敢按严重程度排期 |
| P4 | 没有状态与负责人 | 修到哪一步了不知道 |
| P5 | 没有复扫验证 | 只能说"我改了"，无法证明 |
| P6 | 没有覆盖度校验 | 页面没被爬到 → 告警消失 → **假关闭** |

### 1.2 需求拆解

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| R1 | 书面授权 + 白名单，扫描前强制校验 | 越界目标在扫描前被拒（7 条范围测试） |
| R2 | 能生成/导入结构化扫描报告 | 解析器 10 条测试 |
| R3 | 告警按稳定指纹归并，重复导入不重复创建 | 去重测试 |
| R4 | 显示风险等级、URL、描述、建议 | 平台与界面 |
| R5 | 可设负责人、状态、修复 Commit | 工作流 7 条测试 |
| R6 | 至少 5 条人工复核，记录判定理由 | 9/9 条，见 `docs/renshen_fuhe.md` |
| R7 | 至少修 1 个问题并复扫关闭 | 修了 3 个 |
| R8 | 复扫能区分新增/未变/风险变化/已关闭 | 对比 3 条测试 |
| R9 | 报告脱敏、访问受限、无未授权扫描 | 见 README 第八节 |

### 1.3 非目标

- 不做主动扫描、不做漏洞利用。
- 不部署 DefectDojo（资源重，指导书也说"不是必装项"）。
- 不接入真实生产系统。

## 二、授权与安全边界（第一优先）

### 2.1 授权链

```
课程实验指导书（授权依据）
    ↓
scope.md（资产所有者 / 批准人 / 目标 / 允许时间 / 禁止动作）
    ↓
platform/fanwei-peizhi.json（生效白名单：hosts / ips / urls / 禁用关键词）
    ↓
fanwei.jiaoyan_mubiao(url)（代码级强制校验）
    ↓
shengcheng_saomiao_mingling(url)（校验不过就抛异常，没有绕过入口）
```

### 2.2 门禁规则（6 条）

| # | 规则 |
| --- | --- |
| 1 | 协议必须是 `http` / `https` |
| 2 | host 必须命中 `allowed_hosts`，或是命中 `allowed_ips` 的 IP |
| 3 | **私网地址不自动放行**（`192.168.x.x` / `10.x.x.x` 必须显式配置） |
| 4 | 完整 URL 命中 `allowed_urls` 直接放行，否则回落到 host 规则 |
| 5 | host 含 `forbidden_keywords` → 直接拒 |
| 6 | **重定向到白名单外主机 → 立即停止** |

第 6 条单独写了一个函数 `jiaoyan_zhongdingxiang()`，
因为指导书点得很明确：

> 若采用爬取，显式限制 context/include 范围，并将靶场网络设为隔离网络
> 或通过出口策略阻止越界，**不能仅校验初始 URL 就假定所有后续访问获授权**。

## 三、架构与设计决策

### 3.1 五层结构

```
范围层   fanwei.py     授权门禁（扫描前强制）
解析层   zap_jiexi.py  报告解析 + HTML 净化
指纹层   zhiwen.py     稳定指纹（去重的依据）
存储层   cunchu.py     SQLite + 状态门禁
对比层   duibi.py      before/after 分类 + 覆盖度校验
界面层   app.py        Streamlit（薄封装）
```

**为什么把范围层放在最上面而不是塞进界面里**：
如果门禁写在界面事件里，任何人绕着界面直接调函数就废了。
现在 `shengcheng_saomiao_mingling()` 是第一道也是唯一一道口子，
测试 `test_mingling_bixu_guoyan` 断言它必过校验。

### 3.2 决策一：按 instance 建 Finding，而不是按 alert

ZAP 的 JSON 结构是 `site[] -> alerts[] -> instances[]`。
**一条 alert 可能命中多个 URL**（同一个规则在多处出现问题）。

如果按 alert 建一条记录，就会漏掉其他实例——
一个规则命中了 5 个页面，平台里只显示 1 条，另外 4 个永远没人管。

本实现按 **instance** 建 Finding。测试 `test_duo_shili_bu_lou` 用一个
含 2 个 instances 的 alert 断言会生成 2 条记录。

### 3.3 决策二：稳定指纹只归一化"确实等价"的东西

```
指纹 = SHA256( 规则ID | 规范化origin | HTTP方法 | 规范化路径 | 规范化参数 )
```

| 归一化 | 做不做 | 理由 |
| --- | --- | --- |
| 随机查询值（`_=`、`cachebuster`） | ✅ 做 | 只影响缓存，不改变资源 |
| 参数顺序 | ✅ 做 | `?a=1&b=2` ≡ `?b=2&a=1` |
| 路径里的数字 ID | ❌ **不做** | `/item/1` 和 `/item/2` 是不同资源 |
| 参数名 | ❌ 不做 | `?id=` 和 `?uid=` 语义可能不同 |

**取舍原则**：宁可偶尔多建一条（重复），也不要错误合并（漏掉真实漏洞）。
重复可以人工合并；**漏掉则永远不会被发现**。

### 3.4 决策三：Verified 必须有证据（代码级硬约束）

```python
def gengxin_zhuangtai(..., zhuangtai, ...):
    if zhuangtai == "Verified":
        if not xiufu_commit and not fusaopici:
            raise CunchuCuowu("没有修复 Commit 也没有复扫批次记录，不允许置为 Verified")
```

指导书原文："关闭状态必须有修复 Commit 与复扫证据，不能手工改为 Done。"

这条**不是流程约定，是代码断言**。测试
`test_meiyou_zhengju_buneng_verified` 断言它会抛错，
`test_you_zhengju_ke_verified` 断言补上证据后能通过。

### 3.5 决策四：覆盖度校验防假关闭（自主扩展）

`duibi.py` 不只对比告警集合，还对比**两次扫描的 URL 覆盖集合**：

```python
if len(hou_urls) < len(qian_urls) * 0.8:
    return {"jinggao": "after 扫描的 URL 覆盖明显少于 before，"
                       "不能判定修复。状态只能保持 Resolved。"}
```

**为什么这条最重要**：这是漏洞管理里最隐蔽的错误。
页面没被爬到 → 告警消失 → 看起来"修好了" → 实际问题还在。
平台会给出明确警告并**拒绝**让这些记录进 `Verified`。

## 四、实现要点

### 4.1 HTML 净化

ZAP 报告的 `desc` 和 `solution` 字段含 HTML。
如果直接渲染，就是把**扫描证据当可信 HTML 执行**——
攻击者只要在目标页面的响应里塞一段标签，就能影响平台页面。

`qu_html()` 用 `html.parser` 解析后只保留文本节点，
并做实体解码。测试 `test_qu_html_wu_biaoqian` 断言输出里没有 `<` 和 `>`。

### 4.2 解析器的容错

必须处理的异常情况（每条都有测试）：

| 情况 | 处理 |
| --- | --- |
| 缺 `instances` | 跳过该 alert，不崩 |
| 缺 `pluginid` | 记录为 `unknown`，不崩 |
| 空 `site` 数组 | 返回空列表 |
| 字段类型异常（字符串当数组） | 类型检查后跳过 |
| **alert 顶层没有 url** | 从 instance 层取——这是最容易漏的一点 |

### 4.3 复扫对比的四个类别

| 类别 | 判定 |
| --- | --- |
| 新增 | 只在 after 出现的指纹 |
| 未变 | 两边都有且风险等级相同 |
| 风险变化 | 两边都有但 riskcode 不同 |
| 已关闭 | 只在 before 出现的指纹 |

**注意"风险变化"必须单独一类**：很多对比工具只分"新增/消失"，
风险从低升到中会被算成"未变"而漏掉。
夹具里的 10024 就是专门用来验证这个分类的（riskcode 1 → 2）。

## 五、完整证据链（一条漏洞的闭环）

指导书要求"展示时从平台的一条漏洞追踪到 before 报告、修复
PR/Commit、回归测试和 after 证据"。以 **10020 X-Frame-Options** 为例：

| 环节 | 证据 |
| --- | --- |
| **① before 证据** | `reports/zap-before.json` 中 `pluginid=10020, riskcode=1, instances=2`，位置 `http://localhost:8000/` |
| **② 人工复核** | `docs/renshen_fuhe.md` 第 1 条：判定真阳性，理由"缺少该头页面可被任意站点 iframe 嵌入，存在点击劫持风险" |
| **③ 指派** | 负责人=王锐兵，状态 `Confirmed` → `In Progress` |
| **④ 修复分支** | `fix/10020-10021-10038`（三条安全头一起修，因为都在同一个响应头处理函数里） |
| **⑤ 修复 Commit** | 目标应用 `target/app.py` 的 `zhizao_chuli(anquan=True)` 分支补上三个响应头 |
| **⑥ 回归测试** | `tests/test_xiufu.py::test_xiufu_x_frame` 断言修复版响应里 `X-Frame-Options: DENY` 存在；`test_weixiufu_que_tou` 断言未修复版确实没有 |
| **⑦ 修复不退化** | `tests/test_xiufu.py::test_gongneng_bu_tuihua` 断言修复版仍然返回 200 和正确内容 |
| **⑧ after 证据** | `reports/zap-after.json` 中 **10020 完全不再出现** |
| **⑨ 覆盖度核对** | after 的 URL 覆盖与 before 一致（回环目标固定，无爬取差异） |
| **⑩ 状态** | `Resolved` → **`Verified`**（有 Commit + 有 after 批次） |

**三条一起修的具体内容**：

```python
if anquan:
    tou["X-Frame-Options"] = "DENY"
    tou["X-Content-Type-Options"] = "nosniff"
    tou["Content-Security-Policy"] = "default-src 'self'"
```

**关于 CSP 的一个重要判断**：没有照搬 `default-src 'none'`。
指导书明确警告过：

> CSP 应与页面脚本和资源兼容，不能照搬 default-src 'none' 导致业务不可用。

本目标的页面是纯静态、无外部脚本、无内联脚本，
所以 `default-src 'self'` 既安全又不影响功能。
**照抄最严策略会让页面白屏——那不是修复，那是把服务弄坏。**

## 七、问题与反思

### 7.1 最大的限制：本机没有 ZAP 也没有 Docker

**没有对任何目标执行过真实的 ZAP 扫描。**

指导书对这类情况的态度很明确——作者自己在核验时也写了
"未执行容器启动……不将文档核对表述为容器实测"。

我的处理方式：

- **已实测**：32 条测试全部实跑通过；范围门禁、指纹去重、
  状态门禁、复扫对比都是真实执行的代码路径；
  被测目标应用（未修复版/修复版）是真实可运行的本地 HTTP 服务。
- **未实测**：ZAP 的下载安装、被动扫描、真实报告生成、
  Streamlit 界面的渲染。
- `reports/` 下的两份 JSON 是**人工构造的夹具**，
  严格按 ZAP Traditional JSON 结构编写，用到的规则编号都是 ZAP 真实存在的，
  **但没有编造结果，也没有说成是真实扫描**。

**反思**：如果一开始就先确认环境（有没有 Docker、有没有 Java、有没有 ZAP），
我会更早决定"走夹具 + 完整逻辑实现"这条路，
而不是花时间准备 ZAP 下载脚本。**环境确认应该是第 0 步**——
这一点在实验03 也犯过同样的错。

### 7.2 最认同的一条设计：不让工具代替判断

指导书里有两句话我印象最深：

> 风险等级应完全采用工具评级，还是结合资产、可达性和业务影响？

以及：

> 扫描器不等于结论。

复核 9 条告警的过程让我真切体会到这一点，有两个具体例子：

**例一：10035 HSTS**。工具说"没设 HSTS，风险中"。
但 HSTS **只对 HTTPS 有意义**，本目标是纯 HTTP 本地服务。
无脑加上去反而会让浏览器强制升级到不存在的 https 地址，把演示搞坏。
所以这条判为"接受风险"，**不修**。

**例二：10099 调试信息泄露**。工具判"信息级，风险 0"。
但如果这个应用要对外发布，这条应该是高优先级——
异常堆栈能帮攻击者定位技术栈和内部结构。
**同一个告警在不同部署场景下风险等级完全不同。**

结论：工具评级是**输入**，人要结合资产重要性和业务影响做**判断**，
并且把判断理由记下来——这就是平台要求"处置理由必填"的原因。

### 7.3 关于"假关闭"的认识

一开始我以为"复扫不再出现 = 修好了"。想清楚之后发现这里有四种可能，
只有一种是真修好：

| 可能 | 怎么区分 |
| --- | --- |
| 真的修好了 | 确认覆盖了原页面、规则集相同 |
| 页面没被爬到 | 对比 before/after 的 URL 覆盖集合 |
| 规则没加载 / 规则集变了 | 对比两轮的规则配置 |
| 目标换了（旧容器在跑 / Commit 不对） | 确认目标 Commit 与镜像 |

所以自主扩展选了"覆盖度校验"。这是本实验里我认为最有工程价值的一个设计。

### 7.4 还没解决的问题

1. **ZAP 未实跑**（最大缺口）。
2. **界面未实跑**（Streamlit 未安装）。
3. **没有 SARIF 适配**。指导书把"SARIF/其他扫描器适配"列为可选扩展，
   本次没做。接入多扫描器时指纹算法需要重新设计（不同工具的规则编号体系不同）。
4. **没有 SLA 与逾期提醒**。
5. **人工复核是我自己的判断**，不是安全专家的结论，
   不应该被当作专业安全评估。

## 八、思考题

**1. 扫描器告警在什么条件下才应成为 Confirmed 漏洞？**

三条同时满足：

1. **可达性**——该 URL 在真实部署里能访问到（不是只在开发配置下存在）。
2. **可复现**——人工按告警给的 URI/参数重放一次，现象一致
   （排除扫描器误判和缓存假象）。
3. **影响明确**——说清这条告警在业务上意味着什么风险、影响范围。

只满足"扫描器报了"远远不够。平台要求 `New → Confirmed` 必须填判定理由，
就是把这一步制度化。

**2. 风险等级应完全采用工具评级，还是结合资产、可达性和业务影响？**

结合。工具看不到三样东西：
① 接口是否需要登录（不可达则风险极低）；
② 组件是否真在用（未引用的库不算风险）；
③ 数据在业务上敏不敏感。

正确做法：工具评级作为**输入**，人工结合资产重要性和业务影响**调整**，
并把调整理由记下来。本平台的处置理由必填就是为此。
本文 7.2 节的 HSTS 和数据调试信息就是两个实例。

**3. 稳定指纹如何在避免重复和避免错误合并之间取舍？**

只归一化"确实等价"的：随机查询值、参数顺序。
**不**归一化"可能不等价"的：路径里的资源 ID、参数名。

取舍原则：**宁可多建一条（重复），也不要错误合并（漏掉）**。
重复可以人工合并；漏掉的漏洞永远不会被发现。

**4. 为什么"复扫不再出现"仍可能不足以证明修复？**

因为"不再出现"至少有四种原因，只有第一种是真修好：
① 真修好（且覆盖了原页面、规则集相同）；
② 页面这次没被爬到；
③ 规则没加载或规则集变了；
④ 目标换了（旧容器还在跑 / Commit 不对）。

所以要核对**扫描覆盖范围**、**规则配置**和**目标 Commit**。
本平台的 `duibi.py` 会对比 URL 覆盖集合并给出"覆盖不足，不能判定修复"的警告，
状态只能停在 `Resolved`。

**5. 安全报告中哪些信息需要脱敏，而过度脱敏又会损害什么证据？**

**要脱敏**：Token / Cookie / Authorization 值、真实个人数据、
内网主机名与拓扑、完整技术栈版本号。

**过度脱敏会损害**：如果把 URL 和参数的**具体形态**也模糊掉，
就无法复现问题、无法验证修复、也无法判断两条告警是不是同一件事。

所以边界是：**保留能复现问题的信息（方法、路径、参数名、规则 ID），
抹掉能直接利用的信息（凭据值、真实数据）**。
本平台只处理值，不动结构。
